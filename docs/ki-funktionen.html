🧠 Architektur der KI-Integration

Arrr verwendet eine Provider-Abstraktion, die zwischen zwei Backends umschalten kann:

ProviderTechnologieVorteile
OpenAI-kompatibel HTTP Fetch mit Bearer-Auth an /chat/completions Keine lokalen Ressourcen, hohe Qualität (GPT-4o etc.), schnelle Antwortzeiten
Lokal (llama.cpp) Child Process (llama-server), HTTP-API auf localhost:8080 100% offline, keine API-Kosten, keine Datenweitergabe, kein externes Setup

Beide Provider implementieren das gleiche Interface (AIProvider mit chatCompletion(), healthCheck(), init(), dispose()). Der aiProviderFactory erzeugt einen Singleton-Provider, der bei Settings-Änderungen automatisch neu initialisiert wird.

🔄 KI-Deduplizierung

So funktioniert's

  1. Alle Artikel einer Kategorie werden gesammelt (Titel + Quelle + Datum)
  2. Ein Hash über die Artikelmenge prüft, ob sich seit dem letzten Lauf etwas geändert hat
  3. Die Titel werden als strukturierte Liste an das KI-Modell gesendet
  4. Das Modell gibt ein striktes JSON-Schema zurück: 
    {
  "groups": [
    {
      "canonicalArticleId": "abc-123",
      "duplicateArticleIds": ["def-456", "ghi-789"],
      "reason": "Beide Artikel berichten über das gleiche Ereignis"
    }
  ]
}
  5. Bei ungültigem JSON automatischer Repair-Retry
  6. Duplikate werden in der DB markiert (duplicateGroupId, isHiddenDuplicate)

Auslöser

  • Manuell: Klick auf „Deduplizieren" in der Toolbar
  • Automatisch: Nach jedem Auto-Fetch-Zyklus, wenn aktiviert

Datenfluss

articles (SQLite)
  → getArticlesForDedup()
  → Artikel-Titel als Prompt
  → KI-Modell (Chat Completion)
  → JSON-Response parsen
  → markDuplicateGroup() in DB schreiben
  → UI aktualisiert (Duplikate ausgegraut)
Performance: Eine Eingabe-Hash-Prüfung verhindert unnötige API-Aufrufe. Hat sich die Artikelmenge einer Kategorie nicht verändert, wird der vorherige Deduplizierungslauf verwendet.

🌍 KI-Übersetzung & Zusammenfassung

Deep Translation (Einzelartikel)

Die Funktion translateAndSummarizeArticle() verarbeitet einen Artikel in diesen Schritten:

  1. Cache-Prüfung: Existiert bereits eine Übersetzung für Artikel + Zielsprache?
  2. Prompt-Konstruktion: Titel, Beschreibung und HTML-Body werden an das Modell gesendet
  3. Übersetzung: Das Modell übersetzt den gesamten HTML-Inhalt (h1, h2, h3, p)
  4. Zusammenfassung: Ziel: ca. 500 Wörter, behält die HTML-Struktur bei
  5. JSON-Response: 
    {
  "title": "Übersetzter Titel",
  "description": "Übersetzte Kurzbeschreibung",
  "html": "<h1>...</h1><p>...</p>"
}
  6. Speicherung: In article_translations-Tabelle (SQLite) cachen

Batch-Übersetzung

Die Funktion batchTranslateArticleList() übersetzt alle Artikel in der aktuellen Ansicht nacheinander:

  • Sequenzielle Verarbeitung (ein Artikel nach dem anderen)
  • ~150ms Verzögerung zwischen Artikeln (Rate-Limiting)
  • Per-Artikel Fortschritts-Events an den Renderer
  • Bereits übersetzte Artikel werden übersprungen (Cache)

💻 Das lokale Modell im Detail

Modell

  • Name: Ministral-3-3B-Instruct-2512-Q4_K_M
  • Quelle: HuggingFace (Mistral AI), via modelDownloader.ts
  • Größe: ~1,9 GB Download, ~4–5 GB VRAM im Betrieb
  • Format: GGUF (Q4_K_M Quantisierung)

Server-Management

localLlamaProvider.ts verwaltet den gesamten Lebenszyklus des llama.cpp-Servers:

  • GPU-Erkennung: Prüft nvidia-smi auf CUDA-Verfügbarkeit, konfiguriert GPU-Layer-Offloading
  • Port-Prüfung: Testet, ob der konfigurierte Port bereits belegt ist
  • Prozess-Start: Spawned llama-server als Child Process mit den konfigurierten Parametern
  • Health Check: Pollt /health-Endpoint bis der Server bereit ist (max. 60s Timeout)
  • Graceful Shutdown: Sendet SIGTERM, forced SIGKILL nach Timeout
  • Auto-Warmup: Bei App-Start wird das Modell vorgeladen, wenn der lokale Provider ausgewählt ist

CPU-Fallback

Wenn keine CUDA-GPU erkannt wird und CPU-Fallback aktiviert ist, wird llama-server ohne GPU-Layer gestartet. Die Verarbeitung ist dann ca. 10–20× langsamer, funktioniert aber auf jeder CPU.

Wichtig: Beim ersten Start mit lokalem Modell muss das Modell heruntergeladen werden (~1,9 GB). Der Download erfolgt mit Fortschrittsanzeige und ist abbrechbar. Das Modell wird in {userData}/models/ gespeichert.
